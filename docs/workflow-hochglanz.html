Legende & Akteure im Detail

Martin

Mensch · Owner · einzige Merge-Autorität

  • Rolle: Formuliert Aufträge, entscheidet über Merge (D1)
  • Kommunikation: Telegram-DM oder repo-Thread
  • Merge-Regel: nur bei grünem CI + abgeschlossenem Review
  • Human-in-the-Loop: konzentriert auf den Merge — Agents mergen nie

Hermes Lead (Orchestrator)

Hermes default-Profil am Telegram-Bot

  • Aufnahme: klärt Aufträge, stellt Rückfragen
  • Issues: legt sie mit Template an (Ziel, AK, Scope, Agent-Hinweise)
  • Delegation: Claude Code im eigenen Worktree, Budget-Caps
  • D7: vollendet abgebrochene Runs (unverändert committen)
  • D8: nennt die Basis-Branch bei abhängigen Issues
  • Cleanup: Worktree + Branch nach dem Merge

Researcher

Hermes @research (schnell) / @deep-research (orchestriert)

  • Aufgabe: Recherche, Marktanalyse, Spec-Vorarbeit
  • Output: docs/specs/<feature>.md vor dem Issue
  • Trigger: größere Features (Spec-Gateway im Lead)
  • Vertrag: report.md + quellen.md, Deutsch, Suchdatum

Coder

Claude Code headless · 1 Worktree pro Issue

  • Eingang: Issue mit agent:ready, Pflichtlektüre AGENTS.md
  • Implementiert: im eigenen Worktree, Branch docs/<n>-<slug>
  • Abschluss: push -u origin HEAD, Draft-PR mit Closes #N
  • CI grün → setzt agent:review selbst
  • Sync-Run (D8): fetch + merge origin/main zusätzlich freigegeben
  • Budget: --max-turns; kein dangerously-skip

Reviewer

Claude Code · 2. Run · sauberer Kontext

  • Prüft: AK-Erfüllung, D3 Scope-Treue, D4 DoD, Widerspruchsfreiheit
  • Output: Befunde mit Schweregrad als PR-Kommentar
  • Kein Write/Edit — nur lesend + kommentieren
  • Schleifen: max 2 Fix-Run-Runden, danach needs-human

GitHub CI

GitHub Actions · automatisiertes QS-Gate

  • Checks: YAML-Validierung (Templates, Workflows)
  • Konventionen: AGENTS.md/CLAUDE.md vorhanden
  • Trigger: pull_request + push auf main
  • Grün = Voraussetzung für Draft→Ready und Merge

Hintergrund

Direktiven (AGENTS.md D1–D8)
D1 — Merge nur durch MartinBei vollständig grünem CI. Agenten mergen nie (gh pr merge verboten).
D2 — Budget-Guards--max-turns pro Run; enge allowedTools; kein blankes Bash(git *); Push nur als exakte Form git push -u origin HEAD.
D3 — Kleine PRsEin PR = ein Issue. Keine Scope-Ausweitung ohne neues Issue.
D4 — AkzeptanzkriterienIssue erst erledigt, wenn jede AK-Checkliste abgehakt/verifiziert ist. Rollenfremde Kriterien mit Owner als offen benennen.
D5 — Doku bleibt im RepoErgebnisse, Specs, ADRs → docs/. Niemals nur lokal.
D6 — Keine eigene InfrastrukturNur GitHub + lokale Agenten.
D7 — Abgebrochener Coder-RunLead prüft Worktree (git status/diff/log gegen Basis). Vollständig → Lead vollendet Commit/Push/PR. Unvollständig → Fix-Run. MERGE_HEAD → needs-human.
D8 — Abhängige IssuesBaut ein Issue auf einem offenen PR auf → Worktree von dessen Branch statt origin/main. Basis steht in den Agent-Hinweisen. Nach Vorgänger-Merge: Sync (main holen).
Validierung (Dogfooding)

12 Pipeline-Zyklen

  • • 12 PRs gemerged (PR #2 – #35)
  • • 15+ Issues vollständig abgearbeitet
  • • 0 offene Issues · 0 offene PRs
  • • CI: 12/12 Läufe grün
  • • Review-Schleifen: durchschnittlich < 2 pro PR

Direktiven gewachsen aus Praxis

  • • D7: aus echtem Max-Turns-Abbruch (Issue #7)
  • • D8: aus doppeltem PR-Fall (#10/#12)
  • • Blocker B1: Push-Guard-Umgehung via -C-Wildcards entdeckt und geschlossen (Issue #26)
  • • B5: gh issue edit Blank-Pattern eingeengt (Issue #34)

Sicherheits-Härtung

  • • Kein blankes Bash(git *) — exakte Push-Form
  • • Keine -C/c-Injektion (Wildcard-Angriff verhindert)
  • • gh issue edit nur --add/--remove-label
  • • gh pr edit bewusst nie freigegeben (Body-Sprengkraft)
  • • MERGE_HEAD → needs-human statt Konfliktmarker-Commit
